# Validate guidance against an observed failure — supporting contract

## Authoring recipe and pressure

Descriptions describe observable triggers, not a reason to skip procedure. Stable ids and local exact links avoid runtime prompt downloads. Interpreter invocation avoids executable-bit assumptions.

An omitted citation is corrected with a required citation field; publication without authority needs a permission boundary. Avoid vague exemptions reopening negotiation; real exceptions use observable predicates.

Use realistic urgency/sunk effort/authority/fatigue/missing-tool/ambiguous-evidence pressure. Baseline/candidate solve same task with same capabilities. Self-application is not independent validation. No Anthropic-adapted expression, community policy, hooks or servers are redistributed.

## Presentation and behavioral checks

Use prose/numbered steps for linear actions, a table for lookup, and a small optional decision diagram only when a non-obvious branch benefits. Labels name meaningful states/actions; diagrams do not contain executable code. A Mermaid fragment can stay as text or use the host's existing renderer. Never install Graphviz or auto-generate a project graph just because an upstream helper exists. Check diagram branches against the written procedure; live rendering remains unverified unless actually observed.

Pressure tests can expose automatic deference to authority, commitment to sunk work, scarcity/urgency, social proof and identity claims. State the legitimate rule and its reason, then test whether the consumer preserves it under those pressures. Do not use psychological framing to override the user's authority. Read no-guidance controls and several candidate samples, inspect false-positive matches, and prefer convergent correct actions over verbose rule recital. These authoring techniques are independent guidance, not a redistributed external research document.
