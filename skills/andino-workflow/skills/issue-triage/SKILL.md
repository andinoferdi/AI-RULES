# Turn incoming issues and pull requests into decisions and briefs

Internal method ID: `andino-issue-triage` (alias: `issue-triage`).

> **Andino Workflow Member Skill**
> Operates under Andino Workflow: proportional investigation, evidence-based
> decisions, one durable checkpoint and clean handoff. Do not invoke the workflow
> recursively. Loading this resource changes neither tools nor permissions.

## Purpose

Move each item on the project's issue tracker through a small state machine: give it one
category and one state, check its claim against the code, and leave what the next person
needs: an agent brief, a human brief, needs-info notes or a closing comment. A pull request is
an issue with attached code; it goes through the same states. The maintainer decides; you
gather evidence, recommend, draft and apply exactly what they authorized. A brief written
here is the contract an agent will later build from, days or weeks after the code has moved.

## Trigger and non-trigger

Use when:

- a maintainer asks what needs attention, what is waiting, or what is ready for agents;
- a maintainer names an issue or pull request to look at, evaluate or triage;
- a maintainer tells you to move an item to a state ("move #42 to ready-for-agent");
- earlier triage notes exist and the reporter has replied;
- a request arrives that the project may already have built or already rejected.

Do not select for:

- Building an item that is already ready-for-agent: `plan-execution` or `tdd`.
- Breaking accepted work into a new set of tickets: `writing-tickets`.
- Finding the root cause of a confirmed bug: `debugging` (triage only confirms the claim).
- Reviewing a collaborator's in-flight pull request: `code-review`.
- Re-triaging items the maintainer has just approved, or bulk relabeling the maintainer has
  not itemized.

## Prerequisites

Read the project's tracker configuration (often `docs/agents/issue-tracker.md` or the
`AGENTS.md` section that names the tracker) and record:

- where items live and how to read, comment on, relabel and close them;
- the label string for each of the seven roles below; a project often uses its own strings;
- who counts as a maintainer, so external pull requests can be told apart;
- the required first line for AI-written tracker text; when the project names none, use
  `> *This was generated by AI during triage.*`;
- where rejected requests are recorded (default `.out-of-scope/`), the glossary and ADRs.

When the label mapping is missing, ask the maintainer for the strings before any write and
work in role names until then. A role name written as a label is a wrong label.

## Procedure

1. **Pin the request and its authority.** Sort the request into one or more kinds: attention
   list, named items, state override, resume. For every item write one authority line: what
   the maintainer's own words allow you to change on the tracker. "Look at #12" allows
   nothing; "move #3 to ready-for-agent if it reproduces" allows that change to #3 once the
   condition is observed. Done when every named item has an authority line, and every item
   without one is marked draft only.

2. **Show what needs attention** (attention requests). Read the tracker and sort open items
   into three buckets, each oldest first: never triaged (no category or state label),
   needs-triage, and needs-info with reporter activity after the last triage notes. Include
   external pull requests in the same buckets and tag every line `[issue]` or `[PR]`; a
   maintainer's in-flight pull request is not triage work. Give each bucket a count and each
   item one line. Then let the maintainer pick. Format:
   [tracker notes](resources/tracker-notes.md#attention-list). Done when every open item is
   in a bucket or on the excluded line with its reason (ready state, waiting without a reply,
   maintainer pull request), and items with conflicting state labels are named.

3. **Gather the full context of each item.** Read the body, every comment, the labels, the
   author and the dates; for a pull request also the diff against its base. When earlier
   triage notes exist, list which of their questions are answered and which are still open.
   When an item carries two state labels, stop work on that item and ask which holds. Then
   run two checks against the code, both by domain concept rather than the request's wording:
   - **Already built?** Translate the request into the glossary's terms ("archive" may be the
     project's soft delete), then search the code, CLI help, docs and tests for that behavior. Record
     every place you looked.
   - **Rejected before?** Read every file in `.out-of-scope/` and compare concepts: "user
     scripts" matches a record about a plugin system. See
     [out-of-scope records](resources/out-of-scope.md#matching-a-new-request).

   Done when each item has its answered and open questions, a label-conflict verdict, an
   already-built verdict with the places searched, and a prior-rejection verdict naming the
   matching file or the number of files read.

4. **Verify the claim before any brief.** For a bug, run the reporter's steps or the
   smallest equivalent in a scratch location. For a pull request, check out its branch (or a
   separate worktree), run the tests and the behavior it claims, then return to the starting
   branch. For an enhancement, confirm the current behavior the request builds on. Record one
   verdict: **CONFIRMED** (command, observed output, the code path), **FAILED** (what you ran
   and what happened instead) or **INSUFFICIENT** (which missing detail stopped you: a strong
   needs-info signal). Triage confirms; it does not fix. Done when every bug and pull request
   has a verdict with its command and observed output, or the reason no command could run.

5. **Recommend.** For each item give one category (bug or enhancement) and one state with
   the reason, a short summary of the relevant code, the verdicts from steps 3 and 4, and
   every question for the maintainer. Follow the transitions in
   [roles and states](#roles-and-states); flag an unusual transition and ask before it. Wait
   for the maintainer's direction unless the authority line already covers this item's
   outcome. Done when each item has exactly one category and one state recommendation with
   its reason, and every open question is written where the maintainer will read it.

6. **Grill only what is still open.** When the item needs decisions before an agent can
   build it, work them out with the maintainer one round at a time through
   `andino-brainstorming`, sharpening terms against the glossary and recording settled terms
   and decisions in `GLOSSARY.md` or an ADR as they land. Questions only the reporter can
   answer make the item needs-info. When the maintainer is away, write the questions instead
   of guessing. Done when the brief you are about to write has no open decision, or the item
   stays needs-triage or needs-info with its questions written.

7. **Prepare the outcome artifact.** Write the exact text you would post, first line the
   disclaimer, labels in the tracker's strings:

   | Outcome | Artifact |
   | --- | --- |
   | ready-for-agent | [Agent brief](resources/agent-brief.md); for a pull request, the remaining work on its diff |
   | ready-for-human | The same brief plus why an agent cannot finish it (judgment, external access, design decision, manual testing) |
   | needs-info | [Triage notes](resources/tracker-notes.md#needs-info-notes): what is established, then specific questions for the reporter |
   | wontfix, already built | A comment pointing to where the behavior lives; no `.out-of-scope/` record |
   | wontfix, rejected bug | A polite explanation of why it is intended or will not change |
   | wontfix, rejected enhancement | A comment linking the [out-of-scope record](resources/out-of-scope.md#writing-a-record) you create or extend |
   | needs-triage | The label; a short progress comment only when there is progress to record |

   Done when every item has its artifact as postable text, or a line saying none is needed.

8. **Apply only what is authorized.** For each item whose authority line covers the outcome,
   state in one line what you will change (labels, comment, close, `.out-of-scope/` file),
   apply it, then re-read the item from the tracker to confirm. Apply items one at a time.
   Everything else goes to the maintainer as a draft marked "not posted". Leave the
   repository as you found it: the starting branch checked out, no product code changed,
   nothing committed or stashed. Done when every applied change has been re-read on the
   tracker, every unapplied draft is delivered as not posted, and `git status` shows only the
   intended tracker and `.out-of-scope/` changes.

## Rules for every triage

### Roles and states

| Kind | Role | Meaning |
| --- | --- | --- |
| Category | `bug` | Something is broken |
| Category | `enhancement` | A new feature or an improvement |
| State | `needs-triage` | The maintainer has to evaluate it |
| State | `needs-info` | Waiting on the reporter |
| State | `ready-for-agent` | Fully specified; an agent can build it without asking |
| State | `ready-for-human` | Specified, but needs a person to finish |
| State | `wontfix` | Will not be actioned |

- Every triaged item carries exactly one category and one state. These are role names; use
  the tracker's own strings when writing.
- An unlabeled item normally goes to needs-triage first, and from there to needs-info,
  ready-for-agent, ready-for-human or wontfix. A reporter's reply returns needs-info to
  needs-triage. The maintainer can override any transition.
- For a pull request the states read against the code: ready-for-agent means a brief is
  attached and an agent takes the next step on the diff; ready-for-human means it is ready
  for a person to merge.
- Discovery lists only external pull requests. A pull request the maintainer names is
  triaged whoever wrote it.

### Authority

| The maintainer says | You may |
| --- | --- |
| "What needs attention?", "look at #N", "what do you think of #N?" | Read, run local checks in a scratch location, recommend and draft. No tracker writes. |
| "Move #N to STATE" | Trust it and skip grilling: say in one line what you will change, then apply it. Moving to ready-for-agent without a brief: ask whether they want one written. |
| "If CONDITION, do OUTCOME on #N" | Apply OUTCOME to #N only after you observed CONDITION, and show the observation. |
| A decision on your draft ("close #5", "yes, same as last time") | Apply that outcome to that item, including its `.out-of-scope/` change. |
| An instruction covering items it does not name ("close the stale ones") | List the items it would touch and ask once before any write. |

No instruction here allows changing product code, committing, pushing, or leaving another
branch checked out. A source example or an earlier session never grants a write.

### Resuming earlier triage

When an item carries earlier triage notes, read them first, list which questions the
reporter answered, and present the updated picture before continuing. Never ask an answered
question again; carry everything settled into the "established" part of any new notes.

### AI-written text

Every comment, issue or brief you post or draft for the tracker starts with the project's
disclaimer line. Questions are specific and answerable: name the command, file, version or
observation you need, never "please provide more info".

## Shortcuts that break triage

| Shortcut | What to do instead |
| --- | --- |
| "The listing shows the title and labels, that's enough to judge." | Read the full item and every comment before recommending. |
| "No keyword match in `.out-of-scope/`, so it was never rejected." | Compare concepts. Different words often name the same rejected idea. |
| "Not in the code under that name, so it's new." | Search by the glossary's term and the behavior, and list where you looked. |
| "The reporter's steps look right; I'll write the brief." | Run them. A CONFIRMED verdict makes a far stronger brief. |
| "Two state labels; I'll go with the newer one." | Ask which holds. A conflict is the maintainer's call. |
| "It's already built, so record it as rejected." | Already built is not rejected. Point to the feature; write no record. |
| "Point the agent at the file and line." | Paths and lines go stale. Name behaviors, types and interfaces. |
| "The maintainer said look at it, so I can relabel it." | Looking is not an outcome. Draft and wait. |
| "I'll re-ask everything to be safe." | Re-asking answered questions loses the reporter. Ask only what is open. |
| "The pull request needs work; I'll describe the whole feature." | Describe the remaining work on the existing diff. |

## Red flags

- A recommendation made from a list view, without the item's comments.
- A tracker write the authority line does not cover, or role names written as labels.
- A tracker comment without the disclaimer as its first line.
- A brief with file paths, line numbers or "the thing is broken" instead of behavior.
- A brief without acceptance criteria, or with criteria nobody can check.
- An `.out-of-scope/` record for a bug or for something already built.
- A question in new notes that the reporter already answered.
- A verification claim with no command and output behind it.
- The repository left on a pull request branch, or with changed product code.

## Ownership and permission boundary

Andino coordinates selection, shared progress and final status from evidence; this skill owns
its procedure, resources and checks, which coordinator brevity never truncates. Loading it
grants no authority: tracker writes follow the authority table, and it authorizes no commit,
push, merge, installation or external message beyond the tracker writes the maintainer named.
Without write authority, produce the drafts locally and say they are not posted.

## Output

Report each item with this record, then the drafts. Keep the record in the reply even when
everything was applied.

```text
#<n> [issue|PR] <title>
Category: <bug|enhancement>   State: <role> (<tracker label>)   Was: <labels before>
Verified: <CONFIRMED|FAILED|INSUFFICIENT|NOT RUN> - <command> -> <observed output>
Already built: <where it lives> | no (searched: <places>)
Prior rejection: <.out-of-scope file and its reason> | none (<n> files read)
Earlier notes: answered <...>; still open <...> | none
Recommendation: <state>, because <reason>
Questions for the maintainer: <...> | none
Tracker change: applied <what> and re-read | draft, not posted
```

For an attention request the output is the bucketed list from step 2 instead.

## Verification

Before reporting, confirm:

- [ ] every step's Done when line holds for every item;
- [ ] every bug and pull request has a verdict with its command and observed output;
- [ ] every recommendation names one category and one state, with labels in tracker strings;
- [ ] every draft and posted comment starts with the disclaimer line;
- [ ] every tracker write is covered by an authority line and was re-read after applying;
- [ ] no `.out-of-scope/` record was written for a bug or an already-built request;
- [ ] the repository is on its starting branch with no product code change, commit or stash.

## Worked example and anti-pattern

[The worked example](resources/worked-example.md) takes one bug report from the attention
list through verification, the brief and the authorized write, and shows a declined
enhancement that turned out to be already built.

Anti-pattern: reading the tracker's list view, labelling five items from their titles,
closing a request as a rejected concept because the feature already exists, and posting a
brief that tells the agent to "fix line 150 of handler.ts".

## Fallback

- No tracker access: work from the item text the maintainer pastes and produce local drafts.
- No reproduction possible: record INSUFFICIENT with the missing detail and recommend
  needs-info; never a guessed root cause.
- No label mapping: recommend in role names and ask for the strings before any write.
- No glossary: search by the plain behavior and say the concept check had no glossary.

## Operational example (offline)

The outcome table on two items: an enhancement that already exists closes as wontfix with no
rejection record, and conflicting state labels stop the item for the maintainer.

```python andino-operational-example
import os

def outcome(item):
    states = [label for label in item["labels"] if label in item["state_labels"]]
    if len(states) > 1:
        return {"action": "ask-maintainer", "reason": "conflicting states: " + ", ".join(states)}
    if item.get("already_built"):
        return {"action": "wontfix", "record_rejection": False, "points_to": item["already_built"]}
    return {"action": "recommend", "record_rejection": False}

if __name__ == "__main__":
    state_labels = {"needs-triage", "needs-info", "ready-for-agent", "ready-for-human",
                    "wontfix"}
    built = outcome({"labels": ["needs-triage"], "state_labels": state_labels,
                     "already_built": "invoice export --pdf"})
    assert built == {"action": "wontfix", "record_rejection": False,
                     "points_to": "invoice export --pdf"}
    conflict = outcome({"labels": ["bug", "needs-info", "ready-for-agent"],
                        "state_labels": state_labels})
    assert conflict["action"] == "ask-maintainer"
    raise SystemExit(1 if os.environ.get("ANDINO_NEGATIVE") == "1" else 0)
```
