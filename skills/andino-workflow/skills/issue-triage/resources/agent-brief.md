# Agent briefs

Read this when an item moves to ready-for-agent or ready-for-human. The brief is a comment on
the item and the contract an agent builds from; the original body and discussion are only
context. For an issue the brief describes the change to build. For a pull request it
describes what is left to do on the existing diff: finish it, close its gaps, answer review
points.

## Principles

### Durable, not precise

The item may wait for days or weeks while the code moves. Write the brief so it still holds
after files are renamed, moved or refactored.

- Describe behaviors, interfaces, types and contracts: the function, type, command or config
  shape the agent should find or change.
- Name types and signatures, never file paths or line numbers: those go stale.
- Do not assume today's structure will survive.

### Behavior, not procedure

Say what the system should do, not how to build it. The agent explores the code fresh and
makes its own implementation choices.

| Write | Instead of |
| --- | --- |
| "`ReminderSchedule` accepts an optional `timezone` field; reminders fire at the local time it names" | "Open src/models/reminder.ts and add a field on line 42" |
| "Running `notes search` with no query lists the ten most recent notes" | "Add an if-branch at the top of the search handler" |

### Acceptance criteria an agent can check

Every brief has concrete, independently checkable criteria; the agent uses them to know it is
done. Cover the case reported and the neighbouring cases the same change must handle.

| Write | Instead of |
| --- | --- |
| "A reminder set for 09:00 in `Asia/Jakarta` fires at 02:00 UTC" | "Timezones work correctly" |

### Explicit scope

List what is out of scope, so the agent neither gold-plates nor drifts into adjacent
features.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug | enhancement
**Summary:** one line: what needs to happen

**Current behavior:**
What happens now. For a bug, the broken behavior and the verdict (how it was reproduced).
For an enhancement, the status quo the change builds on. For a pull request, the state of
the diff: what already works and what is missing.

**Desired behavior:**
What should happen when the work is done, including edge cases and error conditions.

**Key interfaces:**
- `TypeOrFunction`: what changes and why
- Command or config shape: the new or changed option and its values

**Acceptance criteria:**
- [ ] Specific, checkable criterion
- [ ] Specific, checkable criterion
- [ ] Specific, checkable criterion

**Out of scope:**
- What must not change
- The adjacent feature that looks related but is separate
```

A ready-for-human brief uses the same template and adds a **Why a person** line naming what
an agent cannot do: a judgment call, external access, a design decision or manual testing.

## Example: bug

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** Recurring reminders skip the day after a daylight-saving change

**Current behavior:**
A daily reminder created before a daylight-saving change fires on every day except the
first day after the change. Reproduced: a reminder at 08:00 `Europe/Berlin` created on
2026-03-27 has no occurrence on 2026-03-29; `next_occurrences(reminder, 3)` returns
03-28, 03-30, 03-31.

**Desired behavior:**
A daily reminder fires once on every calendar day at the same local wall-clock time,
across both daylight-saving transitions.

**Key interfaces:**
- `next_occurrences(reminder, count)`: returns one occurrence per local calendar day
- `ReminderSchedule.timezone`: unchanged; occurrences are computed in this zone

**Acceptance criteria:**
- [ ] A daily 08:00 `Europe/Berlin` reminder has an occurrence on 2026-03-29 at 08:00 local
- [ ] The same reminder has exactly one occurrence on 2026-10-25 at 08:00 local
- [ ] Reminders in a zone without daylight saving keep their current occurrences

**Out of scope:**
- Weekly and monthly recurrence rules
- Changing how reminders are stored
```

## Example: enhancement

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Archive notes instead of deleting them

**Current behavior:**
`notes delete ID` removes a note permanently. There is no way to hide a note and keep it.

**Desired behavior:**
`notes archive ID` hides a note from `notes list` and `notes search` and keeps it in storage.
`notes list --archived` shows only archived notes; `notes unarchive ID` restores one.

**Key interfaces:**
- `Note.archived_at`: new optional timestamp; unset means active
- `notes list --archived`: new flag
- `notes archive ID` and `notes unarchive ID`: new commands

**Acceptance criteria:**
- [ ] An archived note does not appear in `notes list` or `notes search`
- [ ] `notes list --archived` lists exactly the archived notes
- [ ] `notes unarchive ID` makes the note appear in `notes list` again
- [ ] Archiving an unknown ID prints an error and exits non-zero

**Out of scope:**
- Automatic archiving of old notes
- Changes to `notes delete`
```

## Example: pull request

For a pull request, Current behavior describes the diff, and the brief asks the agent to
finish or fix it rather than build from scratch.

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Finish the contributor's `--limit` option for `notes list`

**Current behavior:**
The pull request adds `--limit N` to `notes list`. Verified on its branch: `--limit 3`
prints three notes and the existing tests pass. Two gaps remain: `--limit 0` and negative
values are accepted and print every note, and the option has no test.

**Desired behavior:**
`--limit N` prints at most N notes for N of 1 or more. A value below 1 is rejected with a
usage error and a non-zero exit. Without the option the output is unchanged.

**Key interfaces:**
- The `--limit` option the pull request already adds; keep its name and meaning

**Acceptance criteria:**
- [ ] `notes list --limit 2` prints the two most recent notes
- [ ] `notes list --limit 0` and `--limit -1` exit non-zero with a usage error
- [ ] A test covers one accepted and one rejected value
- [ ] `notes list` without `--limit` prints the same output as before the change

**Out of scope:**
- Adding `--limit` to `notes search`
- Pagination
```

## A brief that fails

```markdown
## Agent Brief

**Summary:** Fix the reminder bug

**What to do:**
Reminders are broken. Look at the scheduler and fix it. The problem is around line 150.

**Files to change:**
- src/scheduler.ts (line 150)
```

It has no disclaimer line and no category, describes the problem vaguely, points to a file
and line that will go stale, gives no current or desired behavior, and has neither acceptance
criteria nor scope.
