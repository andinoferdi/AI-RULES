# Write documents agents can use

Internal method ID: `agent-document-authoring`. Stable technique adapted to Andino ownership.

## Purpose and selection

Make instructions predictable through precise triggers, useful structure and observable completion.

Activate for: Creating/reviewing an agent-facing guide, instruction pointer or durable procedure.

Do not activate for: Stylistic compression that removes behavior or a second native skill/router system.

## Inputs and dependencies

Consumer failure/use case, current document hierarchy, existing conventions, required behaviors and available behavioral evidence.

Use resources progressively: [worked procedure and example](resources/worked-example.md). It is local and self-contained. Optional project tools are discovered when needed, never installed merely to load this method.

## Procedure

1. Identify consumer, distinct trigger branches and observable output. A context pointer names the resource and the conditions to read it; front-load its leading concept and remove synonymous duplicate triggers.

2. Separate ordered actions from consulted reference. Inline what every path needs, disclose branch-only detail behind a local pointer and co-locate a concept's definition/rules/caveats.

3. Give each step an observable and sufficiently demanding completion bound. Preserve required technical operations, acceptance, examples and safety while pruning repetition.

4. Use a compact defined concept where it carries repeated meaning, but avoid invented terminology with no payoff. Prefer positive target behavior; reserve prohibitions for actual hard boundaries.

5. Keep each meaning authoritative in one place. Remove stale claims, cheap environment-lookups restated as cache, and instructions shown not to change consumer behavior.

6. Split by branch or sequence only when the hierarchy earns the cost; extra files without clear pointers hide essential material. Internal Andino guides never add SKILL frontmatter or native registry entries.

7. Evaluate consumer outcomes on representative positive/negative requests. Deterministic structure/examples check different claims from live model invocation; record both honestly.

## Ownership, precedence and permissions

Andino retains discovery, reasoning depth, one durable plan/checkpoint, delegation, permission decisions and final acceptance. This guide contributes the selected technique; it is not a native skill, router or second lifecycle. Current user/project contracts and accepted decisions override upstream defaults. Focus owns communication; Search First owns required external solution research; existing domain/UI sibling ownership and manual-only/denied controls remain authoritative.

Existing scope authorization persists. Local examples use disposable data; real Git mutations, external messages/tracker writes, credentials, global setup, deployments and recurring jobs require their actual authority. A source example never grants it. Preserve user edits, secrets and current staging.

## Outputs and verification

Pointers close locally, required behavior remains, completion bounds discriminate done/not-done and available consumer evidence supports changes.

Apply the worked example to observe an artifact and independent expected outcomes. Its deterministic result proves only that bounded procedure; it does not prove model routing, live host parity or optional external tool execution. Record actual command/tool, current content identity, result and unresolved limits before claiming success.

## Example and anti-patterns

Positive request: “Rewrite this agent procedure so its branch triggers and completion bounds work.”

Negative request: “Delete half the technique just to make the document shorter.”

Shortening by deleting technique, heading-only wrappers, duplicating source of truth, self-reported 'works' or creating one native skill per method.
