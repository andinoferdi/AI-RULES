# Refine One Dependency-Aware Implementation Plan — Supporting Contract

This contract defines the formal specification, schema rules, and behavioral boundaries for generating implementation plans under Andino Workflow. It establishes the standing quality floor and execution invariants for AI agents.

---

## 1. Plan Document Structure

Every accepted implementation plan generated by `andino-planning` must follow this structure. It lives in the active checkpoint (default `docs/exec-plans/active/YYYY-MM-DD-<feature-name>.md` or the target project's designated convention such as `docs/plans/` or `tasks/plan.md`).

### A. Document Header Block

```markdown
# Implementation Plan: [Feature or Subsystem Name]

> **Governance:** Operates under Andino Workflow. Steps use checkbox (`- [ ]`) syntax for deterministic execution tracking.
> **Target Path:** [Path to active plan document]

**Goal:** [One clear sentence stating the observable user or system capability]

**Architecture:** [2-3 sentences describing the technical approach, architectural pattern, and data flow]

**Tech Stack:** [Concrete languages, frameworks, major libraries, and runtime targets]

**Spec Reference:** [Relative path to accepted spec or source requirements document]

### Global Constraints
- [Non-negotiable project constraint: version floors, dependency limits, security boundaries, performance budgets - one line each]

### Review Focus (Implicit Failure Modes)
[Exactly five input classes or failure modes the spec implies but no happy-path test covers, most critical first]
1. [Failure mode 1: e.g., Crash or connection drop during transaction commit]
2. [Failure mode 2: e.g., Concurrent requests with identical idempotency key]
3. [Failure mode 3: e.g., Malformed, empty, or boundary-exceeding payloads]
4. [Failure mode 4: e.g., Partial failure during downstream service interaction]
5. [Failure mode 5: e.g., Unauthorized access or privilege escalation attempt]
```

## 2. The 3-Tuple Task Schema

Every task in the plan represents an atomic, verifiable unit of work adhering to the **3-Tuple Contract**:
`[Target & Interfaces] -> [Delta Actions] -> [Binary Oracle]`

```markdown
### Task N: [Clear Component or Slice Name]

**Files:**
- Create: `exact/path/to/new_file.ext`
- Modify: `exact/path/to/existing_file.ext:start-end`
- Test: `exact/path/to/test_file.ext`

**Interfaces:**
- Consumes: [Exact signatures and types required from earlier tasks or codebase]
- Produces: [Exact function signatures, types, and constants exported by this task]

- [ ] **Step 1: Write failing test**
  [Test function with explicit assertions using exact domain values from spec]

- [ ] **Step 2: Run test to verify failure**
  Run: `[exact test runner command targeting this specific test]`
  Expected: FAIL with `[expected error signal: e.g., ModuleNotFoundError or assertion failure]`

- [ ] **Step 3: Implement minimal signature in target file**
  [Approach note: data structures, library calls. Body is only provided when algorithms are not determined by signature and tests]

- [ ] **Step 4: Run test to verify pass**
  Run: `[exact test runner command]`
  Expected: PASS

- [ ] **Step 5: Verify Review Focus Item X (if owned by this task)**
  Run: `[exact test runner command for edge failure mode]`
  Expected: PASS

- [ ] **Step 6: Commit task deliverable**
  ```bash
  git add exact/paths...
  git commit -m "feat/fix(scope): clear imperative description"
  ```
```

## 3. Vertical Slicing vs. Horizontal Layering

1. **Vertical Slicing Mandate:**
   - Always decompose by user-facing or subsystem capability, never by technical layer.
   - Fold configuration, schema changes, and documentation into the slice that requires them.
   - Each vertical slice must produce working, testable software independently.

2. **Dependency Graph Invariants (DAG):**
   - The dependency graph must be a strict Directed Acyclic Graph (DAG). Circular dependencies (`A -> B -> A`) or dangling dependencies (`A -> unknown_node`) are immediate planning defects.
   - **Shared Write Frontier Guard:** Tasks that modify the same file cannot be parallelized. They must be serialized in the DAG to prevent merge conflicts and state corruption.
   - If a dependency interface cannot be verified from the existing codebase, mark it `UNKNOWN` and isolate it as a focused discovery spike before dependent work begins.

## 4. Adaptive Density Tiers

Plans adjust cognitive density based on task risk and scope:

| Tier | When to Select | Task Structure | Review Focus | Checkpoints |
|---|---|---|---|---|
| **LITE** | 1-2 files, low risk, local refactor, straightforward bugfix | 1-3 tasks, direct 3-step action (Test, Implement, Verify) | 1-2 critical edge cases | Single final verification gate |
| **STANDARD** | 3-5 files, new API endpoint, modular feature slice | Full 3-tuple tasks, explicit TDD micro-steps, exact signatures | 3-5 failure modes | Checkpoint every 2-3 tasks |
| **DEEP** | 6+ files, core migration, multi-service interaction, auth/security | Strict vertical slices, explicit state-machine checkpoints, rollback paths | Full 5 Review Focus items with dedicated test cases | Mandatory integration gates after each phase |

## 5. Dynamic Re-planning & Plan Mutation Protocol

1. **Plan Overwrite Guard:**
   - Never overwrite an existing, incomplete plan (`tasks/plan.md`, `tasks/todo.md`, or active execution plan) that belongs to a different work context without explicit user consent.
   - If revising the current ticket's plan, update the file in place while preserving completed checkboxes and existing evidence.

2. **In-Place Task Patching (Local Deviation):**
   - If a test or runtime oracle fails due to local implementation details (e.g. minor library return type mismatch), repair the task steps in place without re-generating the entire plan.

3. **Re-Baselining Protocol (Boundary Drift):**
   - If runtime discovery invalidates an architectural boundary, public interface contract, or foundational assumption:
     - Stop execution immediately.
     - Document the disconfirming evidence in the checkpoint.
     - Update the downstream DAG tasks to reflect the discovered reality.
     - Obtain user or harness re-approval before resuming execution.

## 6. Task Acceptance and the Standing Quality Floor (Definition of Done)

Per-task acceptance asks: *"Did we build the requested behavior correctly?"*
The project-wide Definition of Done asks: *"Does the code meet the repository's permanent quality and safety standards?"*

Before any task or checkpoint is marked complete, verify:
- [ ] **Functional Correctness:** All test assertions pass against live runtime behavior.
- [ ] **Regression Safety:** No breaking regressions in existing test suites.
- [ ] **Static Analysis:** Native linters (`ruff`, `eslint`, `cargo clippy`) pass with zero errors.
- [ ] **Type Soundness:** Native type checkers (`mypy`, `tsc`, `pyright`) pass cleanly.
- [ ] **Clean Git Working Tree:** Committed with descriptive semantic message; no stray temporary files or uncommitted diffs left behind.
- [ ] **Deterministic NEXT ACTION:** The single next executable step is unambiguously named.
