# Lenses, rubric and examples
Select one useful lens rather than running a ceremonial catalogue.
SCAMPER: substitute a component/audience; combine adjacent jobs; adapt structural analogy; magnify/minimize; put to another use; eliminate; reverse order/roles. HMW names specific outcome/user/tension without embedding a solution. First principles separates established truth from convention. JTBD asks functional/emotional/social jobs in situation→motivation→outcome form. Constraint prompts one day/one feature/no obvious technology/zero budget. Premortem asks why the shipped idea failed in 12 months.
Evaluate user value before feasibility/differentiation. Name 3 actual candidates/current workaround/frequency/switching reason; emotional pain and workaround suggest painkiller, polite praise may be vitamin. Feasibility covers hardest technical dependency, team/expertise/legal constraints, critical path and first time-to-value. Differentiation ranges new capability→10x→new audience/context→better experience→price; builder technology is not automatically user value.
List must-be-true dealbreakers to test before investment, should-be-true adjustable assumptions, might-be-true secondary bets deferred. High-value/high-feasibility first; high-value/low-feasibility needs bounded proof; low-value/high-feasibility only if truly trivial; low/low reject.
One-page output: HMW problem; recommended direction and why; concrete assumption experiment with measure/time/sample; one-job MVP; Not Doing with reasons; open questions.
Worked example 1: restaurant owner wants direct orders; retention of existing regulars may beat a new marketplace. SMS reorder/pickup experiment tests behavior; delivery, POS, discovery and dashboards are non-goals. Permission/compliance for contact sharing is unresolved, never presumed.
Example 2: editor with independent blocks and 2–5 collaborators may test presence/block locks before character CRDT/offline sync. Constraint is observed coordination need, not “modern apps should collaborate.”
Example 3: stale retrospective may fail because action items never happen. One owned experiment with next meeting demo tests follow-through; anonymous input tests safety separately. New tooling is not assumed necessary.
