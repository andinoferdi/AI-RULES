# Execute an accepted slice

Internal method ID: `implementation`. Conditional adaptation: use only for the concrete requested context; upstream beta/frozen status does not imply general readiness.

## Purpose and selection

Build accepted task behavior while preserving one execution owner and current user work.

Activate for: A concrete accepted specification or ready task with implementation authorization.

Do not activate for: Unresolved material product decisions, research-only requests or permission-denied live changes.

## Inputs and dependencies

Existing Andino plan/spec, exact ticket title/reference, blockers, approved edit ownership, current Git state and project verification commands.

Use resources progressively: [worked procedure and example](resources/worked-example.md). It is local and self-contained. Optional project tools are discovered when needed, never installed merely to load this method.

## Procedure

1. Resolve a passed reference through the actual configured tracker or local artifact and state its title. Reject ambiguous bare numbers rather than using an unrelated checklist.

2. Read the current task graph and accepted spec. Reuse verified completed work and check drift. Select ready tasks whose dependencies have accepted integrated results; a remote closed counter can lag reality.

3. Keep one parent-owned checkpoint. Share spec, task and evidence pointers, never duplicate competing plans. Delegate only independent disjoint tasks through the canonical delegation owner and actual available tools.

4. Implement one public behavior at a time through the canonical tdd method when appropriate. Existing agreed seams count; broader architecture changes require their own accepted scope.

5. Run targeted tests and typechecks during relevant slices, then applicable full checks. Review the complete owned diff, including uncommitted and untracked results, through the canonical review owner.

6. Integrate and mark tasks accepted only after inspecting actual changes and verification. Recompute the ready frontier. Do not automatically commit, branch, reset, merge, publish, close remote tasks or clean worktrees.

7. Record exact current evidence, limitations and next action in the existing checkpoint. A useful retrospective insight can be queued if observed; environment improvements never displace the current task by default.

## Ownership, precedence and permissions

Andino coordinates selection, shared progress, resource guards and final status from evidence.
This skill owns its full procedure, required resources, artifact detail and technical
checks. Coordinator brevity/density never truncates these. User/project authority,
Focus/research/domain boundaries and real invocation controls still apply. Native
`andino-implementation` and this guide expose one method, without recursive workflow invocation.

Existing scope authorization persists. Local examples use disposable data; real Git mutations, external messages/tracker writes, credentials, global setup, deployments and recurring jobs require their actual authority. A source example never grants it. Preserve user edits, secrets and current staging.

## Outputs and verification

Accepted behavior works through real interfaces, current project checks pass, owned diff matches scope, blockers reflect accepted results, and all claimed delegation has actual tool evidence.

Apply the worked example to observe an artifact and independent expected outcomes. Its deterministic result proves only that bounded procedure; it does not prove model routing, live host parity or optional external tool execution. Record actual command/tool, current content identity, result and unresolved limits before claiming success.

## Example and anti-patterns

Positive request: “Implement the accepted API task whose schema dependency has passed.”

Negative request: “Explore whether we need this product at all.”

Trusting a worker's 'done', reviewing only HEAD while edits are uncommitted, starting all flat tickets concurrently despite shared files, or using self-authored notes as permission.

## Fallback

Execute sequentially in the permitted checkout when delegation or safe isolation is unavailable. Preserve blocked work and continue independent ready slices.
