# Repair an explanation that did not land

This is a Focus communication resource, not a native skill or another workflow.
Read it when the user says the previous explanation was confusing or asks what a
technical message means. Restore shared understanding using existing evidence;
ordinary clear answers do not need a repair procedure.

## Inputs and boundaries

Use the previous message, the user's stated confusion, known context and the
project's established glossary. This is not a new research or implementation
request, a curriculum, an intentional learning workspace or an opportunity to
edit files. A request to learn a new concept can receive a direct answer; deliberate
cross-session learning belongs to the active workflow's learning method, not Focus.

Focus retains its normal priority, language, tone and completeness rules. With an
active workflow, continue its existing task and progress record. Standalone use
requires no workflow, durable plan, tool, special corpus or installation.

## Repair procedure

1. Identify the main point the user needs and the missing context in the previous
   explanation. Reuse known evidence; confusion alone is not a research trigger.
2. Lead with the practical consequence in familiar words, then give one concrete
   domain example. Introduce necessary terms before using them; keep established
   identifiers such as Order or Invoice where they prevent ambiguity.
3. State consequential assumptions plainly. Remove unexplained process jargon,
   abbreviations and incidental detail without changing technical meaning,
   uncertainty, prerequisites or evidence limits.
4. Check that the new reply answers the actual confusion in the user's language
   and register. Ask one narrow follow-up only when a material ambiguity remains
   and the available context cannot resolve it.
5. Continue the original authorized task after clarification. Explanation repair
   grants no file-edit, research, tool, host, Git or external-write authority.

If the clarification reveals a different learning goal, answer that concept or
hand it to the existing workflow's learning method when appropriate. Do not create
persistent teaching or a second lifecycle merely because the wording needed repair.

## Worked example and acceptance

Original: “The frontier is empty because unresolved predecessor edges remain.”

Repair: “No task can start yet. The API task is waiting for the schema change.
Finish that change first, then the API task becomes ready.”

The repair preserves the original dependency claim, names its consequence and
identifies the concrete prerequisite. It does not claim the schema was changed or
start changing files. If evidence does not identify the actual prerequisite, keep
it unknown rather than inventing the example's schema dependency.

Positive request: “I do not understand your last message about task blockers.
Explain plainly.” Negative request: “Research a new unrelated framework.”

Reject a mere repetition of the same jargon, a different factual answer disguised
as simplification, unsolicited warnings, or editing files during communication
repair. A short analogy can help when its limit is explicit. Acceptance is the
corrected explanation's preserved meaning and relevant context, not a generated
file or an invented claim that the reader now understands.
